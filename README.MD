# Личный кабинет котельной

Две машины, два разных адреса.

| Что | Где |
| --- | --- |
| OpenRemote, уже работает | `https://212.22.82.167` |
| Этот кабинет, только сайт | `http://195.170.163.72:8090/cabinet/` |

Кабинет — обычная страница в браузере. К котлу она не подключается. Она читает и записывает карточки в OpenRemote: температуры, уставки, режимы. OpenRemote на сервере кабинета не запускается.

Сейчас на `212.22.82.167` отвечает OpenRemote `1.31.1`. Область `boiler` там уже есть. Браузер с адреса кабинета этот OpenRemote пока не пускает: это чинится одной строкой в настройке, шаг 1.

На `195.170.163.72` порты 80 и 443 уже заняты. С них приходит ошибка 502 от программы Pingora. Поэтому кабинет открывается на порту **8090**, эти порты он не трогает.

## Что поставить на сервер кабинета

На `195.170.163.72` нужны Docker и Docker Compose второй версии. Проверка:

```bash
docker --version
docker compose version
```

Если второй команды нет:

```bash
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
```

Пользователя, под которым вы работаете, можно добавить в группу docker: `sudo usermod -aG docker "$USER"`, затем зайти на сервер заново.

## Шаг 1. На сервере OpenRemote разрешить кабинет

Это делается на `212.22.82.167`, там, где уже крутится OpenRemote. Кабинет с другого адреса браузер пустит только после этой правки.

Зайдите на сервер OpenRemote и найдите контейнер manager:

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

В колонке образа будет `openremote/manager`. Дальше подставьте его имя вместо `ИМЯ_MANAGER`.

Узнайте, из какой папки его запускали:

```bash
docker inspect ИМЯ_MANAGER --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
docker inspect ИМЯ_MANAGER --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'
```

Откройте этот compose-файл, найдите сервис `manager` и в его `environment` добавьте строку. Адрес пишется без пути и без слэша в конце, порт обязателен:

```yaml
OR_WEBSERVER_ALLOWED_ORIGINS: http://195.170.163.72:8090
```

Если такая строка уже есть и в ней другие адреса, допишите новый через запятую:

```yaml
OR_WEBSERVER_ALLOWED_ORIGINS: http://старый-адрес,http://195.170.163.72:8090
```

Знак `*` означает «пускать всех». Его ставят только одним, без списка адресов. Вместе с конкретным адресом он не работает.

Сохраните файл, перейдите в папку этого compose и перезапустите только manager. База и Keycloak при этом остаются как были:

```bash
docker compose up -d manager
```

Подождите, пока контейнер станет здоровым: `docker ps`. В статусе manager должно быть `healthy`.

## Шаг 2. На сервере кабинета запустить сайт

На `195.170.163.72`:

```bash
git clone https://github.com/VOL0DYA-AG/dashboard-service.git
cd dashboard-service
git checkout cursor/cabinet-standalone-6edb
cp .env.example .env
```

Откройте `.env` и впишите настоящий пароль администратора OpenRemote в `OR_ADMIN_PASSWORD`. Пользователь по умолчанию `admin`. Остальные строки уже стоят на ваши адреса.

Если ветка уже влита в `main`, строка `git checkout` не нужна.

Запуск сайта:

```bash
docker compose up -d --build
```

Первая сборка скачивает Node и nginx и занимает несколько минут. Проверка:

```bash
docker compose ps
curl -s http://127.0.0.1:8090/cabinet/config.json
```

В ответе должно быть `"managerUrl": "https://212.22.82.167"` и `"realm": "boiler"`.

С вашего компьютера страница ещё может не открыться, если на сервере закрыт порт. Откройте его:

```bash
sudo ufw allow 8090/tcp
```

Если `ufw` не используется, откройте 8090 в панели хостинга, в том месте, где задаётся сетевой экран.

Сайт: `http://195.170.163.72:8090/cabinet/`. Пока не входите: сначала шаг 3, иначе страница входа OpenRemote скажет `Invalid parameter: redirect_uri`.

## Шаг 3. Один раз завести вход и карточки котельной

Эту команду тоже выполняют на сервере кабинета, в той же папке. Она ходит на уже работающий OpenRemote и создаёт то, чего ещё нет:

- область `boiler`, если её нет (она уже есть, скрипт это увидит и вторую не создаст);
- пользователя `operator` с паролем `operator`;
- карточки «Котельная, дом 12», котёл, радиаторы, тёплый пол и ГВС;
- разрешение входить с адреса `http://195.170.163.72:8090`.

Повторный запуск новые карточки не плодит. Пароль уже существующего оператора не меняется. Температуры скрипт не двигает.

```bash
docker compose --profile seed run --rm --build seed
```

Дождитесь строк:

```text
Данные заведены.
Кабинет: http://195.170.163.72:8090/cabinet/
```

Если в конце написано `ВНИМАНИЕ` и `OpenRemote отклонил адрес`, шаг 1 ещё не применён или manager не перезапустили. Данные при этом уже могут быть созданы. После шага 1 эту же команду можно запустить ещё раз.

Если написано, что пароль администратора не подошёл, в `.env` неверный `OR_ADMIN_PASSWORD`.

## Шаг 4. Открыть кабинет в браузере

Сертификат OpenRemote самоподписанный и выписан на имя `localhost`, хотя сайт открывается по IP. Браузер каждый раз предупреждает. Пока предупреждение не подтверждено, кабинет не сможет ни войти, ни взять цифры.

1. В том же браузере откройте `https://212.22.82.167`.
2. На предупреждении о сертификате нажмите «Дополнительно», затем «Перейти на сайт» (в Chrome) или «Принять риск и продолжить» (в Firefox).
3. Должна открыться страница OpenRemote. Её можно закрыть.
4. Откройте `http://195.170.163.72:8090/cabinet/`.
5. Вас перекинет на страницу входа OpenRemote, область `boiler`. Логин `operator`, пароль `operator`, если вы не меняли их в `.env`.
6. После входа виден обзор котельной: улица, котёл, контуры, ГВС.

На телефоне ту же ссылку можно вынести на домашний экран. Отдельное приложение ставить не нужно.

## Если страница есть, а котельной нет

| Что видите | Что сделать |
| --- | --- |
| Сайт `195.170.163.72` без порта отвечает 502 | Это Pingora на портах 80 и 443. Кабинет живёт на порту 8090. Добавьте `:8090` в адрес. |
| `docker compose up` пишет, что порт занят | Поменяйте `CABINET_PORT` в `.env` на свободный, тот же порт впишите в `CABINET_URL`, повторите шаги 1 и 3: адрес в OpenRemote должен совпасть с адресом в браузере. |
| `Invalid parameter: redirect_uri` | Шаг 3 не выполнялся или `CABINET_URL` в `.env` отличается от адреса в строке браузера. Поправьте `.env` и снова запустите команду из шага 3. |
| Страница кабинета есть, вместо цифр текст про сертификат или «не смог спросить данные» | Снова откройте `https://212.22.82.167` и подтвердите сертификат. Если уже подтверждали, на OpenRemote нет строки `OR_WEBSERVER_ALLOWED_ORIGINS` из шага 1. |
| «В realm нет котельной» или «не показал карточки» | Ещё раз выполните команду из шага 3 и дождитесь «Данные заведены». |
| Вход есть, цифры стоят на месте и не меняются | Так и должно быть, пока котёл сам ничего не пишет. Для проверки без котла есть демо ниже. |
| Графики пустые | История копит точки только с момента, когда в поля пишут новые значения. Сразу после создания карточек график пустой. |

Полезные команды на сервере кабинета:

```bash
docker compose logs --tail 50 cabinet
docker compose ps
```

Поменять адрес OpenRemote: поправьте `MANAGER_URL` в `.env` и выполните `docker compose up -d`. Сборку заново запускать не нужно, контейнер перечитает адрес при старте.

## Как ходят данные

```text
браузер оператора
   │  открывает страницу
   ▼
195.170.163.72:8090          только файлы кабинета
   │
   │  вход, чтение карточек, запись уставок, живые цифры
   ▼
212.22.82.167                OpenRemote
   ▲
   │  температуры, насос, горелка, авария
   │
контроллер котла
```

Два направления.

1. Котёл пишет в OpenRemote измерения. Кабинет их показывает.
2. Человек в кабинете пишет уставку или режим. Контроллер котла читает это из OpenRemote и применяет на оборудовании.

Пока контроллера нет, в карточках лежат стартовые цифры. Они не двигаются, и котёл от кнопок в кабинете не включается: до оборудования команда дойдёт только когда контроллер начнёт читать уставки.

## Что лежит в OpenRemote

Одна котельная — это несколько обычных карточек `ThingAsset`. Отдельный тип программировать не нужно. У каждой карточки есть поле `cabinetKind`. Котёл, контуры и ГВС — дочерние карточки объекта.

Скрипт из шага 3 создаёт такое дерево. Имя объекта берётся из `PLANT_NAME`.

| Карточка | cabinetKind | Показывает кабинет | Меняет человек в кабинете |
| --- | --- | --- | --- |
| Объект | `plant` | улица `outdoorTemperature`, связь `online`, авария `alarmActive` и `alarmText`, журнал `journal` | ничего |
| Котёл | `boiler` | статус `status`, подача `supplyTemperature`, обратка `returnTemperature`, горелка `flame` | включение `enabled`, предел подачи `maxSupplySetpoint` |
| Контур | `circuit` | помещение `roomTemperature`, подача контура `flowTemperature`, насос `pumpOn` | уставка `setpoint`, режим `mode` |
| ГВС | `dhw` | температура `temperature`, насос `pumpOn` | уставка `setpoint`, режим `mode` |

Статус котла, поле `status`: `heating` (работает), `standby` (ожидание), `off` (выключен), `fault` (авария).

Режим, поле `mode`: `comfort` (комфорт), `eco` (эконом), `antifreeze` (антизамерзание), `off` (выключено).

Числа записываются как числа, флаги как `true` или `false`, статус и режим как текст.

Эконом в кабинете считается так: для помещения уставка минус 3 °C, для ГВС минус 8 °C. Антизамерзание держит помещение около 8 °C и ГВС около 15 °C.

На полях, которые должен видеть оператор, стоит флаг `accessRestrictedRead`. На уставках, режиме и включении котла ещё и `accessRestrictedWrite`. На температурах, которые рисуются на графике, стоит `storeDataPoints`. Скрипт настройки ставит эти флаги сам.

Полям с температурами, статусом, горелкой и насосом флаг `readOnly` не ставят: с ним контроллер тоже не сможет записать значение.

Оператор связан с каждой карточкой дерева отдельно. Связи только с родителем мало, дети тогда не видны. Скрипт связывает все пять карточек.

Вторая котельная — второй родитель с `cabinetKind=plant` и своими детьми. Кабинет показывает первую найденную. Разным домам проще сделать разных пользователей и связать каждого только со своими карточками.

## Как подключить настоящий котёл

Контроллер, шлюз или маленький скрипт рядом с котлом работает от своего пользователя OpenRemote. Этому пользователю дают права читать карточки и писать поля. Роль `restricted_user` ему не дают: с ней он сможет писать только в уставки, а температуры обновить не сможет.

Скрипт настройки такого пользователя не создаёт. Его заводят в Manager, в области `boiler`, и дают роли клиента `openremote`: `read:assets` и `write:attributes`. Затем связывают его с теми же карточками.

Дальше у контроллера два дела.

**Писать измерения.** Это поля без `accessRestrictedWrite`: температуры, `status`, `flame`, `pumpOn`, `online`, `alarmActive`, `alarmText`. Пакет уходит одним запросом:

```bash
curl -k -X PUT "https://212.22.82.167/api/boiler/asset/attributes" \
  -H "Authorization: Bearer ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '[
    {"ref": {"id": "ID_КОТЛА", "name": "supplyTemperature"}, "value": 61.2},
    {"ref": {"id": "ID_КОНТУРА", "name": "roomTemperature"}, "value": 21.4},
    {"ref": {"id": "ID_КОНТУРА", "name": "pumpOn"}, "value": true}
  ]'
```

Ключ `-k` нужен из-за самоподписанного сертификата.

Токен для такого запроса берётся так. Подставьте пользователя контроллера:

```bash
curl -k -s -X POST "https://212.22.82.167/auth/realms/boiler/protocol/openid-connect/token" \
  -d "client_id=openremote" \
  -d "grant_type=password" \
  -d "username=controller" \
  -d "password=пароль"
```

В ответе поле `access_token`. Его и подставляют вместо `ТОКЕН`. Идентификаторы карточек видны в Manager, если открыть карточку: длинная строка в адресе.

**Читать уставки.** Кабинет пишет их в `setpoint`, `mode`, `enabled`, `maxSupplySetpoint`. Контроллер либо спрашивает карточки раз в несколько секунд, либо слушает события. Запрос карточек:

```bash
curl -k -s -X POST "https://212.22.82.167/api/boiler/asset/query" \
  -H "Authorization: Bearer ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{}'
```

Живые события идут по адресу `wss://212.22.82.167/websocket/events?Realm=boiler`. Первое сообщение после подключения: `{"eventType":"attribute","subscriptionId":"controller"}`.

Удобный готовый мост в самом OpenRemote — агент (MQTT, Modbus или HTTP) и связь агента с полем. Тогда запись уставки из кабинета уходит в протокол контроллера, а измерения из протокола ложатся обратно в поля температур. Кабинет при этом не меняется: ему всё равно, кто пишет число, человек, скрипт или агент.

На график попадает поле с флагом `storeDataPoints`. Каждое новое записанное число становится точкой. Запрос истории для одного поля:

```bash
curl -k -s -X POST "https://212.22.82.167/api/boiler/asset/datapoint/ID/attribute/supplyTemperature" \
  -H "Authorization: Bearer ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"type":"lttb","fromTimestamp":0,"toTimestamp":0,"amountOfPoints":240}'
```

`fromTimestamp` и `toTimestamp` — миллисекунды. Нули в этом запросе кабинет заменяет на выбранный интервал: 6 часов, сутки или 7 дней.

Журнал на экране — это текст в поле `journal` у карточки объекта. Внутри лежит JSON-список записей `{ "t": миллисекунды, "level": "info", "text": "что случилось" }`. Уровень ещё бывает `alarm` и `ok`. Если контроллер журнал не ведёт, на экране останутся старые записи.

## Проверка без настоящего котла

В `.env` поставьте `SIM_LOOP=true` и снова запустите:

```bash
docker compose --profile seed run --rm seed
```

Пока эта команда работает, скрипт раз в 5 секунд читает уставки из кабинета и записывает рассчитанные температуры. На экране цифры начинают ползти, смена уставки попадает в журнал. Остановить — Ctrl+C.

Перед подключением настоящего контроллера верните `SIM_LOOP=false`. Два писателя в одни и те же поля будут затирать друг друга.

Шесть часов искусственной истории для графиков: `SIM_BACKFILL=true` на один запуск. Если конкретный OpenRemote запись с меткой времени не примет, в логе будет фраза про историю, и график начнёт копиться с живых значений.

## Что менять, если адреса другие

Три места должны совпадать с тем адресом, который человек набирает в браузере:

1. `CABINET_URL` и `CABINET_PORT` в `.env` на сервере кабинета.
2. `OR_WEBSERVER_ALLOWED_ORIGINS` у manager на сервере OpenRemote. Туда пишется только начало адреса, например `http://195.170.163.72:8090`.
3. После правки `CABINET_URL` ещё раз выполните команду из шага 3, чтобы вход пустил с нового адреса.

`MANAGER_URL` меняют, если переехал сам OpenRemote. Затем `docker compose up -d` на сервере кабинета.

## Что в этом репозитории

- `ui/cabinet` — страница кабинета.
- `contract/plant.ts` — имена полей и правила, по которым карточки OpenRemote превращаются в экран.
- `simulator` — разовая настройка OpenRemote и, по желанию, демо-цифры.
- `docker-compose.yml` — только сайт кабинета и команда настройки. Образов OpenRemote в нём нет.
